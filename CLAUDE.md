# CLAUDE.md — футбольный менеджер как рабочее приложение

Рабочее название проекта пока не выбрано. Это футбольный менеджер для Steam (Windows и macOS), который выглядит и работает как профессиональное клубное ПО в стиле Notion/Linear, а не как аркадная игра.

Перед любой новой функцией прочитай `docs/concept.md`. Решения по стеку и архитектуре — в `docs/stack.md`, журнал решений — в `docs/decisions.md`, текущие задачи — в `docs/tasks/`, макеты экранов — в `docs/design/`, исследования реальных клубных инструментов — в `docs/research/`.

Игра — симбиоз реальных клубных систем (Hudl, StatsBomb, Wyscout, Catapult, Kitman Labs, Iterpro и др.). Воссоздаём функции и процессы, но **никогда не используем их названия, логотипы и фирменный вид** в коде, интерфейсе и данных: в игре у всех инструментов и провайдеров вымышленные названия.

## Общение с пользователем

- Пользователь не программист и полностью полагается на тебя. Общайся с ним по-русски, простыми словами.
- После каждого шага коротко объясняй: что сделано, как это проверить (какую команду запустить, что должно появиться на экране), что дальше.
- Если требование неоднозначное или решение трудно отменить — спроси, прежде чем делать. Мелкие технические решения принимай сам и записывай в `docs/decisions.md`.
- Код, имена файлов, переменных и сообщения коммитов — на английском. Тексты интерфейса — на русском (позже вынесем в локализацию).

## Стек

- Оболочка: **Electron 43** (закреплена ради macOS 12, см. ADR-004) + **electron-vite**, сборка установщиков через **electron-builder**.
- Интерфейс: **React + TypeScript (strict)**, **Tailwind CSS**, **shadcn/ui**.
- Таблицы: **TanStack Table** + **TanStack Virtual**. Командная палитра: **cmdk**. Графики: **Recharts**. Состояние интерфейса: **Zustand**.
- Иконки: **Lucide** (`lucide-react`). Анимации: **Motion** (`motion`).
- Ядро симуляции: чистый **TypeScript** в **Web Worker**, связь с интерфейсом через **Comlink**.
- Данные: **SQLite** через **better-sqlite3** в main-процессе (с задачи T002; в T001 данные в памяти).
- Steam: **steamworks.js**, только в main-процессе.
- Тесты: **Vitest** (логика и ядро), **Playwright** (интерфейс). Линтер: **ESLint** + **Prettier**.
- Не добавляй Unity, Tauri, Rust, другие UI-фреймворки и тяжёлые зависимости без согласования. Новую зависимость добавляй только с объяснением, зачем она нужна.

## Структура репозитория

```
apps/desktop/            Electron-приложение (electron-vite)
  src/main/              main-процесс: окна, IPC, Steam, SQLite
  src/preload/           типизированный мост contextBridge
  src/renderer/          React-интерфейс
packages/sim/            ядро симуляции: чистый TypeScript, без React/DOM/Electron/Node API
packages/shared/         общие типы и контракты между процессами
docs/                    концепция, решения, задачи, отчёты
```

Используются npm workspaces. Если структура меняется — обнови этот раздел.

## Команды

Все команды запускаются из корня репозитория.

- `npm run dev` — запуск приложения в Electron
- `npm run dev:web` — запуск интерфейса в обычном браузере с моком моста (для Playwright и скриншотов)
- `npm run typecheck`, `npm run lint`, `npm test`
- `npm run test:e2e` — Playwright
- `npm run bench` — замеры производительности ядра
- `npm run build` — сборка установщика под текущую ОС
- `npm run format` — автоформатирование Prettier (`npm run lint` проверяет и ESLint, и Prettier)

Для Playwright на новой машине один раз нужен `npx playwright install chromium`. Если Chromium уже установлен в системе (облачные сессии Claude Code), вместо этого задай `PLAYWRIGHT_CHROMIUM_PATH=/путь/к/chrome`.

Правила 1 и 2 ниже частично проверяются ESLint: в `packages/sim` запрещены импорты React/Electron/Node, `Math.random`, `Date.now`, `fetch`, `window`, `document`, `process`.

## Жёсткие правила архитектуры

1. **Ядро изолировано.** `packages/sim` не импортирует ничего из `react`, `electron`, DOM и Node API (`fs`, `path` и т. д.). Всё состояние мира — обычные сериализуемые объекты.
2. **Детерминизм.** В ядре запрещены `Math.random()` и `Date.now()`. Все случайности идут через генератор с зерном (`packages/sim/src/rng.ts`). Одинаковое зерно и одинаковые решения игрока дают одинаковый сезон — это проверяется тестом.
3. **Интерфейс не считает игровую логику.** Он вызывает ядро через API воркера и только отображает результат.
4. **Безопасность Electron.** `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`. Интерфейс получает возможности только через типизированный API в preload. Не отключай изоляцию ради steamworks.js: он работает в main-процессе, интерфейс обращается к нему через IPC.
5. **Интерфейс работает и в браузере.** Мост из preload должен иметь мок, чтобы `npm run dev:web` открывал интерфейс без Electron.
6. **Атрибуты игрока хранятся числами 1–20**, но интерфейс по умолчанию показывает скаутское досье с текстовыми оценками (см. `docs/concept.md`, раздел «Модель игрока»). Сырые числа — только при включённой настройке.
7. **Только вымышленный мир.** В репозитории не должно быть реальных имён игроков, клубов, логотипов. Реальные данные появятся только как моды сообщества.

## Принципы интерфейса

- Desktop-first: плотные данные, мышь и клавиатура, горячие клавиши. Режим планшета — отдельная раскладка только для дня матча.
- Навигация как в Linear: боковое меню, командная палитра Ctrl+K (Cmd+K на macOS), вкладки.
- Темы (светлая и тёмная) и плотность (компактная и комфортная) — через CSS-переменные, без хардкода цветов.
- Без «игровых» анимаций ради анимаций. Переходы короткие и функциональные: наведение 120 мс, раскрытие и сворачивание 150–200 мс, плавное замедление. Анимации появления панелей и списков — через Motion (бывший Framer Motion), наведение — CSS-переходами.
- Иконки только из **Lucide**: 16 px, толщина линии 1.5–1.75, без заливки. Не смешивай наборы иконок.
- Визуальный ориентир — тёмный интерфейс в духе Linear: утопленная панель контента на тёмной подложке, тонкие рамки, почти монохромная палитра, акцентный цвет только для главного действия и статусов. Не копируй фирменные элементы Linear, только принципы.
- **Экраны делаются по макетам пользователя из Claude Design** (ADR-006, ADR-012). Не придумывай экраны сам: если макета для экрана нет — спроси. Макет переносится на наши компоненты shadcn/ui и CSS-переменные из `apps/desktop/src/renderer/src/styles.css`; цвета и размеры из макета становятся переменными, а не хардкодом. Плагин frontend-design — для мелких решений, которых нет в макете.
- Компоненты shadcn/ui добавляются командой `npx shadcn add <имя>` из папки `apps/desktop`; импорты через алиас `@/` (`@/components/ui/...`, `@/lib/utils`).

## Типографика и иерархия

Интерфейс плотный, но у каждого экрана есть ясная иерархия: главное видно с первого взгляда. Иерархию строим начертанием, размером и контрастом, а не большими кнопками. Шкала (шрифт Inter, цифры — JetBrains Mono):

| Роль                             | Размер / начертание         | Пример                                      |
| -------------------------------- | --------------------------- | ------------------------------------------- |
| Заголовок сущности               | 24 / 600, белый             | Имя игрока в досье                          |
| Ключевое значение                | 24 / 500, моноширинный      | Показатели дня на главной                   |
| Значение в карточке-факте        | 18 / 600                    | Стоимость, срок контракта                   |
| Главный объект блока             | 17–18 / 600                 | Следующий матч                              |
| Заголовок секции                 | 15–16 / 600                 | «Оценки по четырём блокам», «Следующий шаг» |
| Текущая страница в шапке, группы | 14–15 / 600                 | «Главная», «Требует решения»                |
| Заголовок виджета или блока      | 13–14 / 600                 | «Доступность», «Таблица»                    |
| Основной текст                   | 13 / 400; важные строки 500 | Строки решений, срочные — 500 и белые       |
| Подписи, метаданные              | 12 / 400–500, серый         | Время, источник, подписи полей              |
| Мелкие метки                     | 10–11                       | Чипы источников, коды MED-14                |

- Пояснение к заголовку пишется в той же строке обычным начертанием и серым: «**Следующий матч** · через 6 дней».
- Выделяем жирным то, на чём строится решение: свой клуб в таблице, уверенные оценки, срочные решения, итог рекомендации.

**Кнопки — три уровня:**

| Уровень   | Вид                                       | Высота | Текст    | Сколько на экране |
| --------- | ----------------------------------------- | ------ | -------- | ----------------- |
| Главная   | Заливка акцентным цветом, тёмный текст    | 32–36  | 13 / 600 | Одна              |
| Вторичная | Светлее фона, заметная рамка, белый текст | 32     | 13 / 600 | Две-три           |
| Тихая     | Только рамка или без неё                  | 28–32  | 13 / 500 | Сколько нужно     |

Иконки-кнопки — 28–30 px. Крупные кнопки 44 px и больше — только в режиме планшета в день матча.

## Окно и адаптивность

Игра работает в обычном окне, как Linear или Finder: его можно растягивать, сужать, разворачивать на весь экран, сворачивать и переносить между мониторами. Качество интерфейса при этом не должно меняться никогда.

- **Перестраивать, а не сжимать.** При сужении окна шрифты, иконки и отступы остаются того же размера. Меняется только то, сколько панелей видно одновременно. Никакого масштабирования картинки.
- **Главное правило раскладки:** область контента не бывает уже 560 px. Если места не хватает, панели уступают по очереди: сначала правая панель уходит в выезжающую, потом меню сворачивается до иконок, потом меню прячется совсем.
- **Точки перестройки по умолчанию:**

  | Ширина окна | Поведение                                                                                                                         |
  | ----------- | --------------------------------------------------------------------------------------------------------------------------------- |
  | от 1440 px  | Меню, основной контент и правая панель видны полностью; правая панель 320 px                                                      |
  | 1200–1439   | Правая панель сужается до 284 px, длинные строки обрезаются многоточием                                                           |
  | 1025–1199   | Правая панель скрыта, выезжает поверх контента по кнопке в верхней панели                                                         |
  | 861–1024    | Меню сворачивается до иконок (60 px) с подсказками; счётчики превращаются в точки                                                 |
  | до 860      | Меню скрыто и выезжает по кнопке или горячей клавише; виджеты встают в одну колонку; вкладки верхней панели — в выпадающий список |

  При переходе через точку раскладка сбрасывается к значениям по умолчанию для этой ширины. Внутри одной зоны ручные переключения и ширины, выставленные пользователем, сохраняются.

- **Минимальный размер окна** 720 × 480 (`minWidth` и `minHeight` у `BrowserWindow`).
- **Окно запоминает** размер, положение, развёрнутость и монитор между запусками. Если монитор отключён — окно открывается на основном.
- **Свёрнутое окно.** Игра продолжает работать: прогон дней и сезона в воркере не останавливается (`backgroundThrottling: false`). После разворачивания интерфейс сразу актуален, без перерисовки «с нуля» и без задержек.
- **Полный экран.** На macOS — системный полноэкранный режим, на Windows — развёрнутое окно и полный экран по F11. Переключение без мерцания: у окна задан `backgroundColor` в цвет темы, белых вспышек нет.
- **Разные мониторы.** При переносе окна на экран с другой плотностью пикселей (Retina ↔ обычный) всё остаётся чётким. Всё, что рисуется на `<canvas>` (тактическая карта, повторы, графики), учитывает `devicePixelRatio` и перерисовывается при его смене.
- **Живое изменение размера.** Во время перетаскивания края окна раскладка перестраивается на лету, без растягивания застывшей картинки и без дёрганий; тяжёлые виджеты перерисовываются с ограничением частоты.
- **Масштаб интерфейса** в настройках: 90, 100, 110, 125%. Реализуется через zoom-фактор Electron (`webContents.setZoomFactor`), чтобы всё оставалось векторным и чётким. Точки перестройки считаются от логической ширины с учётом масштаба.
- **Таблицы** при нехватке места прячут второстепенные колонки по заданному приоритету, а не сжимают текст; горизонтальная прокрутка — крайняя мера.
- Всё векторное: SVG-иконки, CSS, никаких растровых элементов интерфейса. Должно быть чётко на Retina и 4K.
- Эталон поведения — макет главной в Claude Design. Картинки макета лежат в `docs/design/`, если пользователь их добавил.

## Кастомизация

Пользователь может настроить под себя почти всё, как в Linear (ADR-014). Подробный список — `docs/concept.md`, раздел «Кастомизация». Технические правила:

- Все настройки интерфейса хранятся в **профиле пользователя**, отдельно от сохранения игры: раскладка переносится между карьерами. Позже — синхронизация через Steam Cloud.
- У каждой настройки есть значение по умолчанию и «Сбросить». Сломать интерфейс настройками нельзя: ограничения ширины панелей и правило 560 px действуют всегда.
- Схема настроек версионируется; при обновлении игры старые настройки переносятся миграцией, а не сбрасываются.
- Кастомизация — только интерфейс. На игровую логику и ядро она не влияет.

## Совместная работа

- **В начале каждой сессии** сделай `git pull`: документацию обновляет Claude в чате проекта на claude.ai и сам коммитит её в репозиторий (ADR-013). Если появились новые файлы в `docs/` — коротко скажи пользователю, что изменилось.
- Твоя зона — код, конфиги, `docs/reports/` и записи о технических решениях в `docs/decisions.md`. Концепцию, задачи и правила в этом файле правь, только когда этого требует задача или пользователь, и пиши об этом в отчёте.
- Если твои правки в документе столкнулись с чужими — не перезаписывай, объедини и сообщи пользователю.

## Как работать

1. Бери одну задачу из `docs/tasks/`. Начни с плана и покажи его пользователю, если задача большая.
2. Работай небольшими шагами. После каждого шага запускай `npm run typecheck`, `npm run lint` и тесты затронутых частей.
3. Для изменений интерфейса запускай `npm run dev:web`, открывай страницу через Playwright MCP, делай скриншот и сверяй с ожиданием. Сообщай пользователю, что видно на экране.
4. Делай коммит после каждого завершённого шага с понятным сообщением на английском (`feat: ...`, `fix: ...`, `chore: ...`). Никогда не коммить секреты и `.env`.
5. Результаты и замеры записывай в `docs/reports/<ID задачи>.md`.
6. Если решение меняет концепцию, обнови `docs/concept.md` и добавь запись в `docs/decisions.md`.

## Готово, когда

- typecheck, lint и тесты проходят;
- для интерфейса есть скриншот и проверка в обеих темах;
- в ядре есть тесты на новую логику, включая детерминизм, если логика использует случайность;
- отчёт по задаче обновлён, пользователь знает, как проверить результат сам.

## Запрещено

- `any` без комментария с причиной; отключение `strict`.
- Игровая логика в React-компонентах.
- Сетевые запросы из ядра симуляции.
- Удаление или переписывание тестов, чтобы они «прошли».
