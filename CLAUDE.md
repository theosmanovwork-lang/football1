# CLAUDE.md — футбольный менеджер как рабочее приложение

Рабочее название проекта пока не выбрано. Это футбольный менеджер для Steam (Windows и macOS), который выглядит и работает как профессиональное клубное ПО в стиле Notion/Linear, а не как аркадная игра.

Перед любой новой функцией прочитай `docs/concept.md`. Решения по стеку и архитектуре — в `docs/stack.md`, журнал решений — в `docs/decisions.md`, текущие задачи — в `docs/tasks/`.

## Общение с пользователем

- Пользователь не программист и полностью полагается на тебя. Общайся с ним по-русски, простыми словами.
- После каждого шага коротко объясняй: что сделано, как это проверить (какую команду запустить, что должно появиться на экране), что дальше.
- Если требование неоднозначное или решение трудно отменить — спроси, прежде чем делать. Мелкие технические решения принимай сам и записывай в `docs/decisions.md`.
- Код, имена файлов, переменных и сообщения коммитов — на английском. Тексты интерфейса — на русском (позже вынесем в локализацию).

## Стек

- Оболочка: **Electron** + **electron-vite**, сборка установщиков через **electron-builder**.
- Интерфейс: **React + TypeScript (strict)**, **Tailwind CSS**, **shadcn/ui**.
- Таблицы: **TanStack Table** + **TanStack Virtual**. Командная палитра: **cmdk**. Графики: **Recharts**. Состояние интерфейса: **Zustand**.
- Ядро симуляции: чистый **TypeScript** в **Web Worker**, связь с интерфейсом через **Comlink**.
- Данные: **SQLite** через **better-sqlite3** в main-процессе (с задачи T002; в T001 данные в памяти).
- Steam: **steamworks.js**, только в main-процессе.
- Тесты: **Vitest** (логика и ядро), **Playwright** (интерфейс). Линтер: **ESLint** + **Prettier**.
- Не добавляй Unity, Tauri, Rust, другие UI-фреймворки и тяжёлые зависимости без согласования. Новую зависимость добавляй только с объяснением, зачем она нужна.

## Структура репозитория

```
apps/desktop/            Electron-приложение (electron-vite)
  src/main/              main-процесс: окна, IPC, Steam, SQLite
  src/preload/           типизированный мост contextBridge
  src/renderer/          React-интерфейс
packages/sim/            ядро симуляции: чистый TypeScript, без React/DOM/Electron/Node API
packages/shared/         общие типы и контракты между процессами
docs/                    концепция, решения, задачи, отчёты
```

Используются npm workspaces. Если структура меняется — обнови этот раздел.

## Команды

Создаются в задаче T001. Пока их нет — не выдумывай.

- `npm run dev` — запуск приложения в Electron
- `npm run dev:web` — запуск интерфейса в обычном браузере с моком моста (для Playwright и скриншотов)
- `npm run typecheck`, `npm run lint`, `npm test`
- `npm run test:e2e` — Playwright
- `npm run bench` — замеры производительности ядра
- `npm run build` — сборка установщика под текущую ОС

## Жёсткие правила архитектуры

1. **Ядро изолировано.** `packages/sim` не импортирует ничего из `react`, `electron`, DOM и Node API (`fs`, `path` и т. д.). Всё состояние мира — обычные сериализуемые объекты.
2. **Детерминизм.** В ядре запрещены `Math.random()` и `Date.now()`. Все случайности идут через генератор с зерном (`packages/sim/src/rng.ts`). Одинаковое зерно и одинаковые решения игрока дают одинаковый сезон — это проверяется тестом.
3. **Интерфейс не считает игровую логику.** Он вызывает ядро через API воркера и только отображает результат.
4. **Безопасность Electron.** `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`. Интерфейс получает возможности только через типизированный API в preload. Не отключай изоляцию ради steamworks.js: он работает в main-процессе, интерфейс обращается к нему через IPC.
5. **Интерфейс работает и в браузере.** Мост из preload должен иметь мок, чтобы `npm run dev:web` открывал интерфейс без Electron.
6. **Атрибуты игрока хранятся числами 1–20**, но интерфейс по умолчанию показывает скаутское досье с текстовыми оценками (см. `docs/concept.md`, раздел «Модель игрока»). Сырые числа — только при включённой настройке.
7. **Только вымышленный мир.** В репозитории не должно быть реальных имён игроков, клубов, логотипов. Реальные данные появятся только как моды сообщества.

## Принципы интерфейса

- Desktop-first: плотные данные, мышь и клавиатура, горячие клавиши. Режим планшета — отдельная раскладка только для дня матча.
- Навигация как в Linear: боковое меню, командная палитра Ctrl+K (Cmd+K на macOS), вкладки.
- Темы (светлая и тёмная) и плотность (компактная и комфортная) — через CSS-переменные, без хардкода цветов.
- Без «игровых» анимаций ради анимаций. Переходы короткие и функциональные.
- Для визуальных решений используй плагин frontend-design и макеты из Figma, если пользователь дал ссылку.

## Как работать

1. Бери одну задачу из `docs/tasks/`. Начни с плана и покажи его пользователю, если задача большая.
2. Работай небольшими шагами. После каждого шага запускай `npm run typecheck`, `npm run lint` и тесты затронутых частей.
3. Для изменений интерфейса запускай `npm run dev:web`, открывай страницу через Playwright MCP, делай скриншот и сверяй с ожиданием. Сообщай пользователю, что видно на экране.
4. Делай коммит после каждого завершённого шага с понятным сообщением на английском (`feat: ...`, `fix: ...`, `chore: ...`). Никогда не коммить секреты и `.env`.
5. Результаты и замеры записывай в `docs/reports/<ID задачи>.md`.
6. Если решение меняет концепцию, обнови `docs/concept.md` и добавь запись в `docs/decisions.md`.

## Готово, когда

- typecheck, lint и тесты проходят;
- для интерфейса есть скриншот и проверка в обеих темах;
- в ядре есть тесты на новую логику, включая детерминизм, если логика использует случайность;
- отчёт по задаче обновлён, пользователь знает, как проверить результат сам.

## Запрещено

- `any` без комментария с причиной; отключение `strict`.
- Игровая логика в React-компонентах.
- Сетевые запросы из ядра симуляции.
- Удаление или переписывание тестов, чтобы они «прошли».
