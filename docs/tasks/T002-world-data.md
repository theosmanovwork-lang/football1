# T002 — Мир, база данных и календарь

**Цель:** заменить заглушки T001 настоящей моделью мира: вымышленные лиги, клубы, игроки, штаб и скауты с полной моделью данных, сохранения в SQLite, календарь сезона и ход времени по кнопке «Продолжить». После задачи главная и «Состав» показывают данные из ядра, а не из `homeData.ts`.

**Статус:** не начата
**Зависимости:** T001 завершена, стек утверждён. Первый пункт порядка сборки, `docs/concept.md`, раздел 12.

## Что не входит в задачу

- Пространственный движок матча (отдельная задача). Результаты матчей пока даёт быстрая модель-заглушка из T001.
- Тренировки, травмы, нагрузка, трансферы, поведение ИИ-клубов. Здесь только поля в модели данных и пустые таблицы, где это нужно для будущих задач.
- Новые экраны без макетов. Досье игрока (`docs/design/dossier-*.png`) в этой задаче не верстаем, но модель данных должна позволять его построить.

## Шаги

Делай шаги по порядку. После каждого шага остановись, покажи результат и как его проверить, сделай коммит.

### Шаг 1. Модель данных

В `packages/shared` (типы) и `packages/sim` (логика) опиши сущности. Все идентификаторы — строки, все даты — игровые (`YYYY-MM-DD` от игрового календаря), никаких `Date.now()`.

- **Страна, лига** (уровень, число клубов, формат, регион для знания и подписок).
- **Клуб:** название, короткое имя, цвета, стадион, репутация, бюджет (трансферы, зарплаты, данные), состав, штаб.
- **Игрок:** имя, возраст и дата рождения, гражданство, позиции с уровнем владения, рабочая нога, рост и вес; **атрибуты 1–20** по четырём блокам (техника, тактика, физика, психология и характер — список атрибутов как в макете досье и шире, согласуй с `docs/concept.md`, раздел 9); скрытые свойства (потенциал, склонность к травмам, адаптация, амбиции); контракт (клуб, зарплата, срок, пункты); известность.
- **Штаб и скауты:** роль, навыки 1–20; у скаута — регионы, языки, специализация, точность, загрузка.
- **Знание клуба об игроке** (ADR-017): для каждой пары «клуб — игрок» — процент знания по каждому из четырёх блоков и список наблюдений (тип: видео, живой просмотр, агент, проверка личности; дата; скаут; что добавило). Хранить только для пар, где знание отличается от стартового, стартовое вычислять по правилу.
- **Подписки на данные** (ADR-015): провайдер (вымышленный), пакет, регион, что открывает, цена за сезон, срок. В T002 — только модель и одна базовая подписка «своя лига» у каждого клуба.
- **Статистика:** базовые цифры прошлых сезонов (матчи, минуты, голы, передачи — ADR-016) и записи текущего сезона.

Тесты: сериализация мира туда и обратно без потерь; валидация (атрибуты в диапазоне 1–20, у каждого клуба состав 23–30 игроков).

### Шаг 2. Генератор вымышленного мира

- 5 стран, в каждой высшая лига на 18–20 клубов; плюс 2–3 «далёких» региона (по образцу Южной Америки) с одной лигой каждый — для скаутинга с погрешностью. Всего около 6 000–7 000 игроков, свободные агенты.
- Имена — из локальных списков по странам, без реальных людей. Названия клубов и лиг — вымышленные; проверка, что в списках нет реальных клубов из топ-лиг.
- Сила лиг и клубов распределена правдоподобно: топ-клубы, середина, аутсайдеры; молодёжь с потенциалом выше текущего уровня.
- **История до старта:** базовые цифры за 1–2 прошлых сезона, согласованные с уровнем игрока и клуба.
- **Стартовое знание** по правилу из `docs/concept.md`, раздел 9 (своя лига ≈ 60%, другие лиги топ-5 ≈ 40%, второй ряд ≈ 20%, далёкие регионы ≈ 10%, молодёжь ≈ 5%; известность поднимает). Проценты — константы в одном файле, чтобы их было легко балансировать.
- Генератор детерминирован: одно зерно — один мир. Тест на это.

Замер: время генерации мира (цель — меньше 3 секунд), размер мира в памяти.

### Шаг 3. SQLite и сохранения

- `better-sqlite3` в main-процессе (пересборка под Electron — см. ADR-006). Ядро о базе не знает: main сохраняет и загружает сериализованный мир или его таблицы через мост.
- Схема с номером версии и миграциями с первого дня.
- Сохранение — один файл `.sqlite` в папке данных приложения. Команды моста: создать карьеру (зерно, клуб, роль), сохранить, загрузить, список сохранений, удалить.
- Автосохранение раз в игровой день и при выходе; строка «Автосохранение · время» в нижней панели показывает реальное время последнего сохранения.
- Мок моста для `dev:web` хранит сохранения в памяти браузера.

Замер: время сохранения и загрузки мира (цель — меньше 1 секунды каждое).

### Шаг 4. Календарь сезона и ход времени

- Сезон: даты туров по лигам, международные паузы, кубок (пока только даты), трансферные окна (летнее и зимнее — даты, без логики).
- Для своей команды — микроцикл недели с кодами MD (MD-5 … MD, MD+1), как в макете главной.
- Кнопка «Продолжить» и пробел — перейти к следующему событию: день, матч, решение. Пока решений нет, «Продолжить» двигает время на день; в день матча — играет матчи через модель-заглушку и обновляет таблицы.
- Ход времени и прогон матчей — в воркере; интерфейс во время хода не зависает; дата в шапке и «Неделя N» обновляются.

Тест: прогон полного сезона по дням даёт ту же таблицу, что прогон «одним вызовом» из T001, при том же зерне.

### Шаг 5. Данные на экраны

- Главная: следующий матч, таблица, форма соперника, план недели, доступность — из ядра. Блоки, для которых логики ещё нет (решения дня, инсайты, нагрузка), остаются заглушками и помечены в коде.
- «Состав» — временная таблица своей команды на компонентах из T001 (шаг 4) с оценками досье словами. Это не финальный экран: макет «Состава» придёт отдельно.
- Экран «Новая карьера»: выбор зерна, лиги, клуба и роли — простая форма без макета, пометить как временную.

### Шаг 6. Отчёт

`docs/reports/T002.md`: замеры шагов 2–3, размер файла сохранения, что осталось заглушками, вопросы к пользователю.

## Критерий успеха задачи

Можно создать карьеру, прожить сезон по дням кнопкой «Продолжить», сохраниться, закрыть игру, открыть и продолжить с того же места. Мир детерминирован, данные главной идут из ядра.
